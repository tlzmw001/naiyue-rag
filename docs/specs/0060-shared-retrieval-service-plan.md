# Spec0060：团队共享检索服务与更新边界

日期：2026-10-28。状态：总体目标、取消方式和2执行/20排队已由用户确认；0061–0064已本机实现、接线与验收。
全量2424通过，最终wheel干净环境安装与十条共享请求smoke通过；真实Linux材料/模型吞吐尚未验收。
实施记录和具体证据见各分片；Git同步与MCP网络入口仍属后续独立Spec。

## 1. 已确认的产品目标

- 十位成员通过未来MCP入口，共用公司Linux开发机上的知识库与检索服务；上层知识库Agent调用同一检索能力。
- 知识库来自远端Git，支持手动或定时触发同步。查询服务与更新任务分开管理。
- 首先建设独立Python检索服务模块并用库接口验收并发，网络MCP入口后续接入；不把模块可调用等同跨机器服务已交付。
- 覆盖Spec0051首版本机服务的单业务/busy调度约定。现有核心检索与证据合同继续复用。
- 目标机器32核/64GB/无GPU；Mac开发、Windows兼容、Linux实际材料与吞吐验收分别记录。

## 2. 当前事实与原因

ApplicationRuntime._operation在整个query/ingest/documents期间持唯一锁；OpenAI Embedding/LLM Provider
也各有busy锁。HTTP线程池并不能把这一结构变成并发服务。此前受控ASGI取消及真实TCP断开探针均表明：
断开后后台仍持锁，新业务409/application_busy，health200，后台结束后新请求恢复200。
Spec0059解决连续查询重复加载，但单版本可变缓存和客户端生命周期需适配多请求资源所有权。

复用QueryPipeline、HybridSearch、CoreReranker、ResponseBuilder、来源绑定、版本目录和SQLite发布门禁；
新增层负责调度与请求生命周期，不复制召回/排名算法。

## 3. 调度与状态合同

| 项目 | 约定 |
|---|---|
| 同时执行 | 默认2，可配置正整数 |
| 等待队列 | 默认最多20条等待请求，可配置；不含已执行的2条 |
| 调度顺序 | 正常请求按入队顺序分配空闲槽位 |
| 正常十条突发 | 空闲且已就绪时，两条执行、八条排队，不因busy直接拒绝 |
| 队列满 | 明确overloaded；不静默丢弃，不无界积压 |
| 请求期限 | 从服务接收请求开始计算，包含排队与实际执行；正有限秒数可配置 |
| 超时/取消 | 向调用方明确返回终态；排队请求移除，执行中请求发取消信号、协作收尾 |
| 重试 | 服务不自动重试；调用方重发是一个新请求，重新走准入与排队 |
| 槽位归还 | 执行任务真正退出后归还，返回timeout本身不归还槽位 |

必须分别表示“调用方已得到timeout/cancelled”和“后台执行已退出”。执行中的超时任务在收尾期间仍计入并发，
不能因调用方重试而突破执行上限。取消、完成、超时之间的竞争只允许产生一个对外终态。
运行中的底层IO/本地推理可能要等已有调用返回；第一版不强制杀线程或重建进程，不保证原生永久阻塞可自动恢复。
阶段切换和可中断循环检查取消/剩余期限；网络调用采用剩余期限与既有网络超时中的较小值。
独立服务的超时不依赖HTTP连接是否仍在；入口以后负责把用户取消映射到服务请求。

配置片应独立定义检索配置，旧配置缺少新节时可加载。当前模板service.request_timeout_seconds为180秒，
可作为新检索配置默认值的来源参考；HTTP客户端等待与服务作业期限必须明确区分。

## 4. 资源归属与版本合同

调用方→请求准入/队列→执行槽位→固定版本资源→既有检索链→结构化证据。

- 每请求：request ID、查询/范围、期限、取消信号、trace/用量、终态；不相互覆盖。
- 每执行槽位：拥有有可变请求状态的模型客户端；不把当前带busy锁的同一个Provider无条件共享给两条请求。
- 每知识库版本：共享已校验资料、索引和只读派生资源；同步初始化，避免同版本并发重复全库解析。
- 查询开始实际执行时选择并固定一个活动版本；有expected_revision则保留原冲突校验。
- 请求固定版本到后台退出，即使调用方已超时，也不提前关闭其客户端或释放版本资源。
- 活动版本切换只需短暂协调；旧版本仍有在途请求时保留。单请求失败不能清理其他请求占用的资源。
- 资源关闭失败必须记录并保留明确的待处理所有权，不把丢失引用当清理成功。
- 文件变化检查区分业务资料/发布标记与已知Chroma维护写入，不能无条件接受冷加载期间业务文件的变化。

Chroma本地嵌入模式的客户端创建/关闭约束继续遵守；锁范围按资源收窄，不仅删除ApplicationRuntime总锁。
不通过多进程同时维护同一本地索引目录绕过现有锁。查询与更新并行必须用原生组件验证。

## 5. 更新与Git同步边界

手动/定时触发→获取远端Git→固定commit→准备独立材料快照→候选构建/校验→按revision发布。
同一知识库更新串行协调；查询在构建期间继续使用已发布版本。发布成功才让后续查询选择新版本；
失败保留原活动版本，并返回可观察的同步/构建错误。同步记录关联commit与最终知识库版本。
定时和手动触发消费同一更新入口；仓库/分支、凭据来源、触发周期在Git同步专属Spec讨论，
不是检索调度实施的前置输入。本阶段不创建真实定时任务、不修改用户Git目录。

## 6. 实施分片

1. 调度与请求生命周期：独立服务配置、2执行/20排队、FIFO准入、请求期限、协作取消、唯一终态及槽位回收。
2. 真实检索资源接线：执行槽位客户端、版本资源复用与持有计数、既有检索链、缓存并发边界及失败关闭。
3. 更新与查询并行：复用摄取/发布流程，候选构建期间查询旧版、发布后新版选择、旧版在途请求继续完成。
4. 分发与容量验收：Python库调用十条突发、取消/异常恢复、原生索引、安装包及跨平台验证；Linux实测2路/4路比较。

Git来源同步的具体实现、Agent、MCP网络入口分别制定后续Spec，不混入检索算法或假称已接通。
现有CLI/HTTP调用迁移到新服务的范围应在接线片明确；保持公开API和既有行为回归，不把旧入口仍串行当新模块已验收。
预计跨越8个以上文件及新增服务模块；生产源码每文件不超过500行，实施片先列精确文件清单。

## 7. 验收与回退

- 事件同步控制：十条同时提交均获受理；至少两条实际执行重叠，队列有界且顺序明确；第21条等待请求才触发容量拒绝。
- 排队取消/超时后不执行模型；执行中超时立即形成调用方终态，后台退出前不归还槽位，重试不突破上限。
- 某请求取消/失败不清理另一条的资源；每次查询仍编码，来源/证据/版本/用量不串线。
- 原生Chroma/BM25并发与重复查询；新版本构建时旧版可查，失败不切换，发布后新旧在途请求各自完整绑定。
- 关闭停止准入，排队任务明确终态，等待活动任务按既定超时收尾；永久阻塞的人工恢复边界明确展示。
- 两个已发现缓存问题有独立失败回归；正式清单/全量测试、构建和发行内容检查通过。
- Linux记录材料规模、2路/4路执行数、等待/执行/总耗时分布、峰值内存及错误率；不以Mac替身测试宣称十人性能通过。

回退恢复原适配/运行时接线并关闭新服务，保留知识库目录、模型和真实配置；不自动回滚活动版本或删除历史资料。
发布/push及公司机部署继续遵守单独授权。L1模块/配置/测试/文档存在；L2调度/控制/版本持有实现；
L3独立库入口→真实检索链、原生双索引、并发更新和最终安装包均已调用验证，不等同Linux容量通过。
