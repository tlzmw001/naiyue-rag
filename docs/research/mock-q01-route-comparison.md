## 2. A：片段检索，补充已有文档关系

候选数据流：Markdown读取/切分 → 片段关键词及向量索引；同时保留显式文档引用、需求与用例名称配对 → 查询片段 → 从有关文档扩展候选 → 对候选正文再次筛选 → 证据组装。

本例可检查的路径：

1. 新需求的显式链接到策略 L1；该 L1 的导航列出历史001和002。因此无需模型抽图就有查旧公式与拆分规则的线索。
2. 找到有关历史需求后，通过名称配对定位旧用例文档；仍需检索具体用例行，不能把整份文件都当相关证据。
3. 字段命名003不在新需求的直接链接里。可以通过内容检索找到；也可从系统/预测模块导航扩展，或建立已有链接的反向查询。反向查询是候选适配机制，本项目尚未实现。
4. 范围扩展必须有跳数、候选数及正文相关性约束。共享 L1 或经 L0 连通不意味着所有下级文档都相关。

关键词检索按词项匹配排序；向量检索按文本表示的相似度找候选。两者都能返回多文档片段，但不能据此裁定旧行为仍有效。

参考项目的真实查询链是 `HybridSearch.search` → dense/sparse 召回 → `_fuse_results` → RRF；已有引用扩展和用例配对是我们的候选补充，不是所读参考链已经具备的功能。[Modular 固定源码](https://github.com/Jerry-ai-dev/MODULAR-RAG-MCP-SERVER/blob/f658c5a4011c8b826707a65a3b11ce9301b0626f/src/core/query_engine/hybrid_search.py)。

## 3. B：LightRAG 的图与片段结合

已核验的源码链：摄取片段 → LLM抽实体/关系 → 合并图节点/边并保留来源 → 实体、关系及片段向量索引。查询 `query_data/aquery_data` → `kg_query` → `_build_query_context` → `_perform_kg_search` → 回查来源片段、预算裁剪及结构化结果。[静态源码笔记](../../research/naiyue-rag-knowledge-base/deep/lightrag.md)。

本例期望检查的图关系可能包括：`p`与`prediction.probability`的字段映射；派生分对原始概率/价值的计算依赖；输出头冲突与回退规则；旧用例与相关行为。这些关系尚未被抽取，不能保证默认提示词能得到它们，更不能保证公式或跨文档用例配对完整。

`mix`结合实体/关系检索与片段向量检索；`naive`只走片段向量，可作同框架对照。`query_data`跳过答案生成，但摄取抽图及查询关键词提取仍可能调用LLM；Embedding、重排也须另计。[LightRAG 固定数据查询出口](https://github.com/HKUDS/LightRAG/blob/453dce83d6d0354a06e46c8d4029a0895c4e054b/lightrag/lightrag.py#L4876)。

图可能帮助关联没有互链但共享概念的内容，也可能把原始概率与校准后概率误合并，或把旧校准规则和新例外合成一句描述。必须回到来源原文验证；图摘要不能替代证据。默认出口不足以满足我们完整的相对路径、原始行号、源版本契约，仍需适配和验证。

特别注意：若本次需求参与抽图，仅在最终结果排除它的文档ID，不保证消除它对合并图描述的贡献。选型实验可把新需求只作任务输入、暂不参与历史图摄取，并记录当前L1仍含本次导航；这是拟议实验边界，不是已实现的源范围能力。

## 4. 两条路线都要处理的局部变更

合成公式 `0.2 * 5 * 2 = 2`；历史gain=1.5时派生输出为3；新需求明确该派生分跳过gain，因此相同算例应输出2。旧用例仍能提供构造与旧行为依据，旧断言却不能直接当新预期。这个判断来自结合原文，不来自相似度、链接或图节点。

需求章节可先比较通用递归切分与标题切分；用例还须核验完整行、维度/列名、部分前置引用及超限处理。A/B都面对这个摄取问题，图不会自动修复被拆坏的用例。具体解析组件尚未选定；不假定自写全部Markdown语法。
